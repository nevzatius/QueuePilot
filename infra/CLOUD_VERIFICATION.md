## Isolation and execution limits

Use only an owner-approved, labeled demo project. First complete the main `bootstrap` stage to prepare APIs/platform agents and the two custom queue roles. Do not change `qp-process`, `qp-api`, `qp-worker` or their runtime identities for probes. Keep a separate non-secret config outside the repository with the same project identity and the probe image digest in **both** image fields. Owner builds the probe image from the root with `scripts/spike/Dockerfile` and pushes it to the demo repository after approval; no such build/deployment was run here. The Dockerfile installs locked dependencies, runs as non-root and uses Node 24. For a strictly reproducible base, the owner must record/pin the resolved base-image digest before building.

Print `node scripts/spike/setup.mjs --config D:/QueuePilot-local/spike.json` and inspect it. Apply one stage at a time using `--apply --approve-project=ACTUAL_DEMO_PROJECT`: `identities`, `queues`, `access`, `deploy`, `iam`, `scheduler`. Ensure the main access stage has granted the Tasks/Scheduler platform-agent roles. Probe setup leaves new queues and the scheduler paused. Explicitly resume only the queue needed for the current check; C9 and the first half of C2 require a paused queue. A new job has a brief create-to-pause interval; use its isolated success endpoint only.

| Resource | Bound |
|---|---|
| `qp-spike-semantics`, `qp-spike-retry`, `qp-spike-slow` | Each 1 dispatch/s, 1 concurrent dispatch, 3 attempts **and** 120 s retry window; no unlimited retries |
| `qp-spike-slow` | 130 s fixed backoff to distinguish duration-first exhaustion |
| `qp-spike-worker` | Private; 0–1 instance, concurrency 1, request timeout 60 s, 1 CPU/512 MiB |
| `qp-spike-hosting` | Public; same compute bounds; separate identity with no data/secret permissions; only `/api/auth-header` responds |
| `qp-spike-scheduler` | Paused; one manual run for C6, then pause/delete |
| Test volume | At most 20 unique tasks in total; at most 2 delay tasks concurrently for the first saturation attempt; never an unbounded load loop |
| Wall clock | 10 minutes per retry/backoff observation; stop if inconclusive. C2 uses bounded observations up to 24 h only with separate owner approval, without a long-running process |
| Redis | PING only, 20 warm sequential samples/request, 2 s connect/command timeouts, 3 repetitions, at most 60 PINGs total |

Allow the owner token creation on `qp-spike-reader` and `qp-spike-no-get` only; probes use the IAM Credentials API to impersonate them for 600 s. This is separate from their own `actAs` permission on `qp-spike-invoker`. Reader has queue-scoped create/get, no-get has queue-scoped create only. Neither receives tasks list/fullView/delete or project-wide Tasks grants. Owner creates/deletes tasks using their provisioning identity where deletion is required. Secret access is limited to the probe worker account. Check inherited IAM does not accidentally grant either probe identity getTask.

The probe CLI defaults to a credential-free JSON plan. To execute, add `--run --approve-project=ACTUAL_DEMO_PROJECT` to each call below and replace the example config path. Append stdout to evidence only after inspecting it for credentials. It reports status codes and safe attempt metadata, never an OIDC/access token or task payload. HTTP errors are observations, not automatic test PASS results.

After creation preserve the exact returned task ID. All task OIDC tokens target `qp-spike-invoker`; audience is the exact private probe worker origin.
